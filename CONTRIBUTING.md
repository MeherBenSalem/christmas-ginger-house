# Contributing

Thanks for contributing to Christmas Ginger House.

## Before you start

- Open an issue or discussion for substantial changes before investing in a large implementation.
- Keep changes focused. Avoid unrelated refactors in the same pull request.
- Preserve compatibility-sensitive identifiers (`mod_id` `christmas_ginger_house`, package `tn.nightbeam.christmasgingerhouse`, registry IDs) unless a change explicitly requires them.

## Development workflow

1. Fork the repository and create a branch from `main`.
2. Make the smallest coherent change that solves the problem, in the relevant Minecraft version workspace
   (`1.20.1/`, `1.21.1/`, `26.2/` or `26.3/`).
3. Textures, models, data and sounds are generated by `tools/assets/build_all.py`; `tools/assets/targets.py`
   translates the data for each Minecraft version (26.3 has its own data format). Shared datapack sources live in
   `shared/resources/`.
4. Build the workspace you changed (`./gradlew build` from that folder: Gradle on Java 21 for 1.20.1 and 1.21.1,
   Java 25 for 26.x), or all four with `./gradlew buildAll` from the root (the 8 loader jars land in `releases/`).
   On 26.2 and 26.3 this also runs the Fabric server game tests.
5. Update documentation when behavior, configuration, or release steps change.
6. Open a pull request with a clear summary, verification notes, and any compatibility risks.

## Coding expectations

- Follow the existing patterns in the targeted version root. The version folders are intentionally isolated.
- Keep loader entry points thin; put shared logic in `common`. Do not add mixins unless a real feature needs them.
- Do not port changes across versions with shared sources or symlinks.
- Avoid committing generated jars, logs, run directories, secrets, or local IDE files.

## Reporting issues

- Use GitHub issues for bug reports and feature requests.
- Include the Minecraft version, loader, mod version, reproduction steps, and relevant logs when possible.
